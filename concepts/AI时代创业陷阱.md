# AI 时代创业陷阱

AI 工具让创业更快，也让创始人更容易掉入特定陷阱。以下是各阶段最危险的失误模式。

## Idea 阶段的三大陷阱

### 1. 把建造误当验证
**本质：** 原型 ≠ 问题存在的证据

历史上 42% 的创业失败原因是建了没人要的东西。AI 让"有想法 → 立即建原型 → 把原型当验证"的错误路径成本极低，因此这个失败模式只会更严重。

- 一个能运行的原型很容易被误当作"真实需求存在"的证明
- 正确用法：原型是和潜在用户对话的**道具**，不是验证本身
- 验证的真正来源是人的反应，不是代码的运行

### 2. 过早扩展
**本质：** AI 移除了所有自然瓶颈，可以在业务需求验证之前就把执行规模扩大

> "It will generate, test, debug, and refactor a codebase around a fundamentally flawed premise with exactly the same enthusiasm it brings to a great idea."

Agentic coding 可以为错误的前提构建和正确想法同等质量的代码库。扩展执行不等于验证了方向。

### 3. AI 加持的确认偏见
**本质：** 问 AI 支持你已有信念的证据，它会找到

- 创始人天生对自己的想法充满热情 → 创业圈的职业病
- 现在 AI 给了确认偏见一个"研究引擎"：让 AI 帮你验证你的 TAM，它会给出让你满意的数字
- 解药：**主动让 AI 做结构化反方**——让它找反对证据、分析竞争对手为什么会赢、压力测试你最依赖的假设

## MVP 阶段的三大陷阱

### 4. Agentic 技术债（复利型）
**本质：** 没有书面架构约束 → 每次 session 重新推导决策 → 代码库结构逐渐混乱

普通技术债可以在 dedicated sprint 中清掉；Agentic 技术债是复利的：
- 跳过 specs 和架构文档的创始人会碰到可预见的墙
- 每个新 session 都会从头推导基础决策，这些决策互相漂移
- 最终得到功能正常但结构混乱的代码库——没有任何单个部分是坏的，但各部分从未被设计成能配合在一起的
- 迟早会强制从头重建

**解药：** 在写第一行代码前，创建 CLAUDE.md 作为架构上下文文档；每次 session 开始读它，结束时更新它。

### 5. 假 PMF（发布能量 ≠ 真实牵引力）
**本质：** 早期的热情来自关系网络，不是真实需求

"发布能量"的来源：创始人的朋友、Hacker News 头条、投资人关系网络的 portfolio 公司。这些在第 6-12 周消散后不再可靠。

**解药：**
- 在第一个用户到来**之前**就定义度量框架
- 定义你的产品的"假阳性"长什么样（如：有注册但无激活、有收入但无留存）
- PMF 双信号：Sean Ellis 测试（>40% 用户说失去产品会"非常失望"）+ 努力测试（从推 → 拉的转变）

### 6. 零摩擦功能蔓延
**本质：** 每个单独决策都合理，累积起来失去方向

用 agentic coding 时，每个新功能只要一个下午。"当然应该处理这个边缘情况；当然用户会想要这个流程。" 单看都成立，但产品会越长越远离原始边界。

**解药：** 事先写好 Scope 文档，包括：
- 产品**做什么**
- 产品**刻意不做什么**
- 功能新增标准：什么样的用户证据才足以新增功能

## 跨阶段的隐性陷阱

### 创始人成为瓶颈（Launch 阶段）
MVP 阶段的"事事亲力亲为"是资产，在 Launch 阶段变成约束。

**征兆：**
- 决策需要一周才能处理
- 支持请求堆积，因为只有你知道答案
- 运营任务只在你想起来时发生

**解药：** 做运营负担审计，把每件事分类：
- 可完全自动化
- 需要人但不必须是你
- 真正需要创始人判断

### 过早扩张市场（Launch 阶段）
新市场带来：新用户行为、新合规要求、新支付基础设施。结果是：
- 失去解读自己数据的能力（变量太多）
- 同时风险忽略原始用户群

初始牵引力是真实的，但它是针对你的早期受众特定的。
