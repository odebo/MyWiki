# AI Harness 工程架构模式

来源：一蛙AI 抖音视频《深入AI Harness演讲探讨了人工智能治理框架》（~19分钟，2026-06）

---

## 核心定义

**AI Harness = 套在 LLM 外面的确定性环境。**

模型负责"想"，Harness 负责"管"。不改 prompt，不换模型，通过工程化外壳让不稳定的 LLM 输出变得可预期、可回滚、可审计。

---

## 四个核心组件

| 组件 | 职责 | 类比 |
|------|------|------|
| 工具注册表（Tool Registry） | 声明模型可用哪些工具、如何调用 | 能力边界说明书 |
| 上下文管理（Context Management） | 精准控制每步骤喂给模型的信息 | 按需投喂，不是全倒 |
| 安全护栏（Safety Guardrails） | 行动前检查是否符合规则，结构性拦截 | 不靠模型自觉，靠框架约束 |
| 自动验证（Auto Validation） | 输出后检查结果，不符合要求自动重跑 | logic validator |

---

## 核心洞见：不确定性是架构问题

LLM 的概率性不是 bug，是架构本质。

- 改 prompt = 跟模型谈判，依赖理解力和运气
- 加 Harness = 给模型划定操作手册，出边界自动重来

用梁宁的"系统能力"框架理解：ATM 的确定性不靠钞票本身，靠七个岗位的系统协作。AI 产品的确定性不靠模型，靠 Harness 这层工程基础设施。

> 聪明的模型 + 混乱的环境 = 聪明的错误。普通的模型 + 严格的 Harness = 稳定的输出。

---

## 与 Anthropic Harness 的区别

| 维度 | Anthropic Harness（[[Anthropic-harness-design-long-running-apps]]） | 一蛙AI Harness |
|------|------|------|
| 核心关注 | 创意任务 Eval 困境、审美评分框架 | 系统可靠性、确定性工程 |
| 解法焦点 | 生成器/评估器分离、外化审美标准 | 四组件外壳、减少 prompt 依赖 |
| 适用场景 | 创意/设计类 Agent | 通用业务流程 Agent |

两者互补：Anthropic 解决"好不好"的问题，一蛙AI 解决"稳不稳"的问题。

## IBM Oprahag 案例

企业级落地场景。大型企业对 AI 的核心诉求：
- 可控（每层组件显式）
- 可审计（出问题有迹可查）
- 可回滚（修复有地方下手）

Harness 天然满足三点，比"微调黑箱模型"更适合企业侧。

---

## 未来方向：动态 Harness 生成

一蛙AI 预测：系统将根据任务自动组装所需的约束层，不需要人工预先定义每个组件。这是通向 AGI 的关键工程步骤。

**Harness 工程师**将成为 AI 落地的稀缺技能——类比 [[FDE前沿部署工程师模式]]，填补模型能力与系统可靠性之间的 gap。
