# Eval 设计：定义"成功长什么样"

来源：Cat Wu（Claude Code 产品负责人）访谈。
核心命题：**10 个好 eval 胜过 100 页需求文档。定义"成功"，本身就是最核心的产品工作。**

---

## 为什么 Eval 是最被低估的 PM 技能

Eval 不是测试工程师的活——它测的不是"代码实现是否符合规格"，而是"规格本身定得对不对"。写 eval 的过程，就是把模糊的"好"翻译成明确的、可测试的"好"——这是**产品判断力的外化**。

Cat Wu 写 eval 时，产出常常不是"通过了"或"没通过"，而是"这个功能还需要更明确的产品定义"——eval 在她手里是思考工具，不只是验证工具。

---

## Memory 案例：四类高 Eval 需求特征

Memory（AI 记忆功能）完美展示了传统产品管理方法全部失效的情形：

### 特征一：判断型（没有客观对错）
代码对不对可以跑测试验证。"AI 该不该记住这件事"——你随口提了一个偏好，要不要存？需要判断力，且判断质量无法被脚本自动测量。

### 特征二：静默失败型（失败滞后发现）
代码失败立刻报错。Memory 失败可能三周后才发现——模型引用了一个过时的记忆，导致回答跑偏。

> **失败和发现失败之间的时间差，是所有 AI 产品最危险的敌人。**

### 特征三：高风险非对称型（多了比少了更危险）
大多数功能"不 work → 得不到价值"。Memory 多了一层危险："不精准 → 被错误信息误导"。成功标准不是 recall rate，而是 precision——**宁可漏记，不可错记**。

### 特征四：复合效应型（质量随时间累积）
单次对话质量不累积。但 memory 的质量跨对话累积——一次错误存储会污染未来所有相关对话。评估必须测随时间推移的行为序列，不能只测单次。

---

## 四类特征作为识别器

有了这四类特征，你就能判断**什么功能最需要 Eval**：

| 特征 | 需要 Eval？ |
|------|------------|
| 判断型（没有客观对错） | 高度需要 |
| 静默失败型 | 高度需要 |
| 高风险非对称型（做错比不做更糟） | 高度需要 |
| 复合效应型（质量随时间累积/衰减） | 高度需要 |
| 有即时反馈闭环 | 不需要花太多精力 |
| 成功标准可自动验证 | 不需要花太多精力 |
| 失败后用户立刻知道且容易恢复 | 不需要花太多精力 |

**判断什么该写 eval、什么不该，本身就是品味。**

## 北极星指标 vs Eval：体温计 vs 血检

| 维度 | 北极星指标 | Eval |
|------|-----------|------|
| 测量对象 | 系统输出在用户世界的效果（统计性） | 系统能力边界（诊断性） |
| 信号 | 聚合的、滞后的、归因模糊的 | 固定输入、可复现、精确指向失败原因 |
| 用途 | 告诉你"出问题了" | 告诉你"出在哪、怎么修" |
| 比喻 | 体温计（发烧了） | 血检（白细胞偏高、细菌感染、用哪种抗生素） |

大多数团队的诊断工具箱里只有体温计——出了问题只能知道"出问题了"，不知道出在哪。

---

## 核心结论

在传统软件时代，"定义成功"分散在产品需求文档、设计评审、测试用例、上线复盘里——分散意味着没有人负全责。在 AI 时代，eval 把它们收敛到一个地方：

> **当模型的行为不是板上钉钉确定的时候，"成功"的定义需要比以往任何时候都更精确。一个好 eval，胜过一百页需求文档。**
